## Установка

Одна команда — выберите свою оболочку. Она добавляет этот репозиторий как маркетплейс
плагинов и ставит мод для вашего пользователя: он загружается в каждой новой сессии, и в
терминале, и в десктопном приложении Claude.

**macOS · Linux · Git Bash на Windows**

```bash
claude plugin marketplace add Gerrux/claude-load && claude plugin install claude-load@claude-load --config language=auto
```

**Windows — PowerShell** (5.1 и 7)

```powershell
claude plugin marketplace add Gerrux/claude-load; if ($?) { claude plugin install claude-load@claude-load --config language=auto }
```

**Windows — командная строка** (`cmd`)

```bat
claude plugin marketplace add Gerrux/claude-load && claude plugin install claude-load@claude-load --config language=auto
```

**Только десктопное приложение Claude** (команды `claude` в терминале нет): нажмите **+**
рядом с полем ввода → **Plugins** → **Add marketplace** → `Gerrux/claude-load` → **Add plugin**
→ **claude-load**.

**Внутри терминальной сессии Claude Code:**

```text
/plugin marketplace add Gerrux/claude-load
/plugin install claude-load@claude-load
```

Затем в уже открытой сессии выполните `/reload-plugins` и `/load`.

| | |
| --- | --- |
| **Нужно** | Claude Code с поддержкой модов, 2.1.287 или новее (`claude --version`); Windows 10/11, macOS или Linux |
| **Язык** | `--config language=auto` следует языку Claude Code, затем локали системы. Закрепить язык: `en`, `ru`, `de`, `es`, `fr`, `pt`, `zh` или `ja`; поменять позже — в `/config` |
| **Обновить** | `claude plugin marketplace update claude-load`, затем `claude plugin update claude-load@claude-load`, затем `/reload-plugins` |
| **Удалить** | `claude plugin uninstall claude-load@claude-load` (и `claude plugin marketplace remove claude-load`) |

## Зачем

Запустите несколько сессий Claude Code параллельно — у каждой субагенты, MCP-серверы,
dev-серверы и тесты, — и машина ползёт, а диспетчер задач показывает стену `node` и
`claude`. claude-load раскладывает нагрузку **по сессиям**:

| | |
| --- | --- |
| 📊 **По сессиям** | CPU, память, число процессов, самые тяжёлые процессы внутри, график CPU за 6 минут |
| ⚠️ **Сироты** | dev-процессы, у которых умер родитель (vite-сервер, языковой сервер, забытый запуск Python), приписаны к своему репозиторию или worktree по рабочему каталогу; завершаются в один клик после подтверждения |
| 🧩 **Всё остальное** | прочие процессы, сложенные по имени (`chrome ×31`), — видно, Claude ли вообще виноват |
| 🔎 **Фильтры и группировки** | все · активные · тяжёлые · сироты · это окно; по сессиям, по репозиториям (worktree сворачиваются в основной), по процессам; сортировка по CPU или памяти |
| ✻ **Разобрать с Claude** | одна кнопка: встроенный скилл `sessions-triage` раскладывает простаивающие сессии и сирот, спрашивает один раз и архивирует или завершает только одобренное |
| ⏳ **Очередь запусков** | `runq` ставит тяжёлые запуски всех сессий в очередь по памяти, эксклюзивным тегам и диску; защита, которую включают по желанию, направляет их туда |
| 🚦 **Строка нагрузки** | над полем ввода при высокой нагрузке (CPU от 50% или память от 85%), с главными потребителями |
| 🌍 **8 языков** | English, Русский, Deutsch, Español, Français, Português, 中文, 日本語 |

## Использование

| Команда | Что делает |
| --- | --- |
| `/load` | Открывает пейн и печатает в чат краткий отчёт |
| `/load all` | То же, со всеми простаивающими сессиями |
| `/load band on` · `off` · `auto` | Строка нагрузки над полем ввода: всегда, никогда или только при высокой нагрузке (по умолчанию) |

В пейне:

- **процессы** раскрывает сессию: её процессы по именам и тяжёлые PID.
- **завершить** у процесса или сироты завершает его вместе с дочерними после
  **Да, завершить**. Перед этим PID ещё раз сверяется со свежим снимком и именем процесса.
  Собственные процессы сессий (`claude`) и PID, которых нет в текущем снимке, отсюда
  завершить нельзя.
- **открыть ↗** переключает на эту сессию в десктопном приложении Claude.
- **✻ Разобрать с Claude** просит Claude в текущей сессии разобрать нагрузку. Архивировать
  сессии можно только с инструментами десктопного приложения; в терминале Claude подскажет,
  что закрыть.

Фильтр, группировка и сортировка запоминаются между сессиями.

**Язык:** настройка плагина `language` (`/config`) принимает `auto`, `en`, `ru`, `de`, `es`,
`fr`, `pt`, `zh` или `ja`. `auto` берёт настройку `language` Claude Code, затем локаль
системы, затем английский.

## Очередь запусков (runq)

Несколько сессий на одной машине запускают по ресурсоёмкому прогону (набор тестов,
симуляцию, большую сборку), и машине не хватает памяти, или два прогона с общими
временными путями мешают друг другу. `runq` заставляет их ждать своей очереди сами:
каждая тяжёлая команда стоит в одной очереди на всю машину, пока для неё не найдётся
место, и затем запускается как обычно.

```bash
python "$HOME/.claude/state/queue/runq.py" --mem 20 --tag helios --label "scan 1 ha" -- ./target/release/treegrow-cli scan --plot 1ha
```

Эта же строка работает в Git Bash и в PowerShell (`$HOME` раскрывается в обоих; в других
местах используйте `python3`). Нужен Python 3.8 или новее. Мод копирует `runq.py` в
`~/.claude/state/queue/` при каждом старте сессии, поэтому путь не меняется при
обновлениях плагина.

Задача ждёт в порядке поступления, пока не выполнится всё из этого:

- **память:** свободный commit (что Windows ещё может пообещать: ОЗУ плюс файл подкачки)
  покрывает `--mem` задачи плюс запас, по умолчанию 12 ГБ. Запущенные задачи считаются с
  тем, что они заявили и ещё не заняли, поэтому две задачи, допущенные с разницей в
  секунду, не видят одну и ту же свободную память. Меньшая задача может обогнать большую,
  которая ждёт памяти; когда большая прождала 5 минут, её не обгоняет уже ничто, что
  требует памяти.
- **эксклюзивные теги:** ни запущенная задача, ни задача, вставшая в очередь раньше, не
  держит тот же эксклюзивный тег. `cargo-test` эксклюзивен по умолчанию: один
  `cargo test` на машину.
- **диск:** на каждом диске `--disk D:=<ГБ>` свободно столько места, за вычетом того, что
  запущенные задачи заявили для него и ещё не записали.

Затем runq запускает команду как собственный дочерний процесс с stdin, stdout и stderr
терминала и завершается с кодом выхода команды. Собственные строки runq идут в stderr и
начинаются с `runq:`: строка о ходе ожидания каждые 30 с (почему он ждёт), а в конце —
выход, время работы и пиковая память.

| Параметр | |
| --- | --- |
| `--mem <GB>` | ожидаемый пик памяти прогона (обязателен; `0` для прогона, которому нужен только тег) |
| `--tag <name>` | можно повторять; эксклюзивный, если указан в `exclusiveTags` |
| `--disk D:=<GB>` | можно повторять; сколько места должно быть свободно на диске (на macOS/Linux — путь) |
| `--label <text>` | как пейн и журнал называют задачу (по умолчанию — команда) |
| `--max-mem <GB>` | завершить дерево процессов самой команды, если оно превысит это значение |
| `--max-wait <min>` | сдаться после такого ожидания (выход 75) |

| Выход | |
| --- | --- |
| код команды | она выполнилась |
| 2 | ошибка использования |
| 3 | `--mem` плюс запас больше предела commit машины: запуститься не смогла бы никогда |
| 75 | истёк `--max-wait` |
| 126 | команду не удалось запустить (например, свежесобранный `.exe`, который блокирует Microsoft Defender: `Permission denied`); сообщается один раз, без повторов |
| 127 | команда не найдена |
| 130 | отменена (Ctrl+C) во время ожидания |
| 137 | завершена собственным `--max-mem` |

`runq.py status` показывает, что запущено и что ждёт (и почему), свободный commit, ОЗУ и
диски; `runq.py log --since 30m` (или `-n 50`, время в ISO, `--json`) показывает события:
queued, started, finished, killed, failed, stale, cancelled, gave-up. Пейн показывает то же
в разделе **Очередь запусков**, пока что-то запущено или ждёт, и ещё два часа после.

**Что трогает runq.** Память чужих процессов он читает только через общие итоги машины.
Единственные процессы, которые он когда-либо завершает, — дерево его собственной команды, и
только с `--max-mem`. В Windows команда работает в Job Object: её дерево — это ровно члены
задания, каждый проверяется на принадлежность заданию перед завершением, а убитый runq
уносит с собой команду, а не оставляет её работать без учёта. Где задание создать нельзя (и
на macOS/Linux), дерево обходится по родительскому PID, и у каждого процесса перед
завершением проверяется время старта. Задача, у которой не осталось ни runq, ни команды
(сбой, перезагрузка), удаляется по PID и времени старта; команда, продолжающая работать
после смерти своего runq, сохраняет место и теги. Решения принимаются под файловой
блокировкой ОС, которую ОС снимает, когда её владелец умирает.

**Настройки:** `~/.claude/state/queue/config.json`, все необязательны:

```json
{
  "guardGB": 12,
  "exclusiveTags": ["cargo-test"],
  "fairAfterMin": 5,
  "guard": {
    "roots": ["C:/Users/me/garage/treegrow", "D:/work/treegrow-*"],
    "rules": [{ "name": "cargo test", "pattern": "^cargo(\\s+\\+\\S+)?\\s+(test|nextest)\\b", "tag": "cargo-test", "memGB": 8 }]
  }
}
```

### Защита: тяжёлые команды только через runq

В проекте, который её включил, команда Bash или PowerShell, запускающая тяжёлый прогон в
обход runq, отклоняется, а агент получает точную строку runq, которую нужно выполнить
вместо неё (с сохранёнными `cd …&&` и `| tail`). Сам мод никогда не переписывает и не
запускает команду. Включите защиту для проекта в его `.claude/settings.json` (общий, так
что она действует во всех его worktree) или `.claude/settings.local.json`:

```json
{ "env": { "CLAUDE_LOAD_RUNQ_GUARD": "1" } }
```

или для папок, включая worktree, через `guard.roots` в `config.json` (`*` заменяет одну
часть пути); `"0"` в настройках проекта выключает её там. Тяжёлыми по умолчанию считаются:
`cargo test` / `cargo nextest`, `treegrow*` `grow|scan|stand|forest` (исполняемый файл или
`cargo run … -- <verb>`) и `helios*`; `guard.rules` заменяет этот список.

## Как это работает

Один сэмплер на машину пишет `~/.claude/state/load/snapshot.json`; мод каждой сессии только
читает его раз в 5 секунд, поэтому стоимость не растёт с числом сессий.

- **Windows:** скрытый процесс PowerShell (`sampler/load-sampler.ps1`), его запускает мод.
  Каждые 4 секунды он читает `Get-Process`, а дерево родителей из CIM — только когда
  появились новые процессы, и выходит через 3 минуты после закрытия последней сессии.
  Замер на машине с 12 потоками и 15 сессиями: около 0,35% CPU и 130 МБ памяти.
- **macOS и Linux:** мод одной из сессий держит «аренду» и снимает нагрузку через `ps`; если
  эта сессия закрылась, другая подхватывает за 15 секунд.

Сессия — это PID из `~/.claude/sessions/<pid>.json`, её нагрузка — всё её дерево процессов.
Сирота — дерево процессов, у которого умер родитель (на macOS и Linux — переподчинённое
`init`, `systemd` или `launchd`) и внутри есть dev-инструмент. Его рабочий каталог берётся у
самого процесса (Windows читает его из памяти процесса, Linux — из `/proc/<pid>/cwd`,
macOS — через `lsof`).

**Приватность:** всё остаётся на вашей машине. Никаких сетевых запросов и телеметрии.

## Проблемы и решения

- **«Сэмплер не запускается»** (Windows): скрипты PowerShell запрещены политикой
  (`AllSigned` или Constrained Language Mode). Сэмплеру нужно запускать
  `sampler/load-sampler.ps1` из папки плагина.
- **На macOS/Linux ничего не видно:** проверьте, что `ps` есть в `PATH`; `lsof` (macOS)
  нужен только для сирот.

## Статус

Разрабатывается и каждый день используется на Windows 11 с десктопным приложением Claude.
Сэмплер для macOS и Linux покрыт юнит-тестами на записанном выводе `ps`, `vm_stat`,
`/proc/meminfo` и `lsof`, но на настоящем Mac или Linux ещё не запускался. Отчёты и
исправления приветствуются.
